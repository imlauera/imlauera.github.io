Guía práctica para administrar Proxmox VE desde SSH, sin depender de la interfaz web. Los ejemplos están pensados para un nodo simple; en este equipo el nodo se llama home.

Estado del sistema

Comandos útiles para ver el hardware y la carga antes de tocar VMs:

hostnamectl
pveversion -v
lscpu
free -h
swapon --show
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS,MODEL
ip -br a
qm list
pct list
pvesm status

En este equipo (Acer Aspire ES1-311, Pentium N3540, 4 cores, 7.6 GiB RAM, HDD 500 GB) el cuello de botella principal es RAM + disco mecánico. Si la RAM asignada a VMs supera la física y entra swap, el sistema se vuelve muy lento.

Ajuste de RAM realizado

Se bajó la asignación de memoria para evitar sobrecomprometer el host:

VMID Nombre Antes Después
100 debian-chromium 4096 MiB 2048 MiB
101 freebsd 2048 MiB 1024 MiB
102 macos-prebuilt 6144 MiB 4096 MiB

Comandos usados:

qm set 100 --memory 2048
qm set 101 --memory 1024
qm set 102 --memory 4096
qm config 100 | grep memory

Nota: cambiar el límite de RAM en Proxmox no es lo mismo que ajustar el uso dentro del guest. Si la VM estaba corriendo, conviene reiniciarla o verificar si el cambio aplica en caliente según el guest/configuración.

qm: máquinas virtuales (QEMU/KVM)

Usalo para VMs: Linux, FreeBSD, Windows, macOS, etc. Cada VM tiene su propio kernel.

# Listar y ver estado
qm list
qm status 101
qm config 101

# Ciclo de vida
qm start 101
qm shutdown 101 --timeout 60   # apagado limpio por ACPI
qm stop 101                    # apagado forzado (como cortar energía)
qm reboot 101
qm reset 101                   # reset duro

# Consola/monitor
qm terminal 101                # requiere consola serial configurada en el guest
qm monitor 101                 # monitor QEMU; comandos: info status, quit

# Cambiar recursos
qm set 101 --memory 1024
qm set 101 --cores 2
qm set 101 --onboot 1
qm set 101 --name freebsd-lab

# Disco
qm resize 101 scsi0 +5G        # agranda disco; después ampliar FS dentro del guest

# Snapshots
qm snapshot 101 pre-cambio --description "antes de actualizar"
qm listsnapshot 101
qm rollback 101 pre-cambio
qm delsnapshot 101 pre-cambio

# Clonar / borrar
qm clone 101 201 --name freebsd-clone --full
qm destroy 101 --purge         # BORRA VM y discos asociados; peligroso

SSH a una VM FreeBSD

FreeBSD no puede correr como LXC porque necesita su propio kernel. Se usa VM. Si la VM no tiene guest agent o consola serial, arrancala y obtené su IP desde la red o la consola web:

qm start 101
qm status 101
ip neigh show dev vmbr0        # MAC/IP vistas en el bridge

Dentro de FreeBSD, habilitar SSH:

ifconfig                       # ver IP
sysrc sshd_enable=YES
service sshd start
# opcional: permitir password o agregar clave en ~/.ssh/authorized_keys

Desde tu máquina:

ssh usuario@IP_DE_FREEBSD

pct: contenedores LXC (solo Linux)

LXC es liviano porque comparte el kernel del host Linux. Sirve para Debian, Ubuntu, Alpine, etc. No sirve para FreeBSD, Windows o macOS.

# Plantillas
pveam update
pveam available --section system
pveam download local debian-12-standard_12.7-1_amd64.tar.zst

# Crear contenedor
pct create 200 local:vztmpl/debian-12-standard_12.7-1_amd64.tar.zst \
  --hostname ct-debian \
  --memory 512 \
  --cores 1 \
  --rootfs local-lvm:8 \
  --net0 name=eth0,bridge=vmbr0,ip=dhcp \
  --unprivileged 1 \
  --password

# Ciclo de vida
pct list
pct start 200
pct enter 200                  # shell root dentro del CT
pct exec 200 -- apt update
pct shutdown 200
pct stop 200

# Configuración
pct config 200
pct set 200 --memory 1024 --cores 2
pct resize 200 rootfs +2G

# Snapshots
pct snapshot 200 pre-cambio --description "antes de cambios"
pct listsnapshot 200
pct rollback 200 pre-cambio
pct delsnapshot 200 pre-cambio

# Borrar
pct destroy 200 --purge        # BORRA contenedor; peligroso

vzdump: backups

Hace backup de VMs y contenedores. El modo y compresión dependen del storage y del tipo.

# Backup de una VM
vzdump 101 --storage local --mode snapshot --compress zstd

# Backup de un contenedor
vzdump 200 --storage local --mode stop --compress zstd

# Backup de todos
vzdump --all 1 --storage local --mode snapshot --compress zstd

# Ver backups existentes
ls -lh /var/lib/vz/dump/
pvesm list local | grep backup

Restaurar:

# Restaurar VM (a mismo VMID o uno nuevo)
qmrestore /var/lib/vz/dump/vzdump-qemu-101-*.vma.zst 101 --force

# Restaurar contenedor
pct restore 200 /var/lib/vz/dump/vzdump-lxc-200-*.tar.zst --storage local-lvm

--force sobreescribe. Revisá antes de usarlo.

pvesm: almacenamiento

Administra storages definidos en Proxmox: directorios, LVM, LVM-thin, NFS, etc.

pvesm status                   # capacidad/uso
pvesm list local               # contenido
pvesm list local-lvm
pvesm path local:iso/debian-13.iso

# Agregar directorio como storage (ejemplo)
# pvesm add dir backupdir --path /mnt/backup --content backup,iso,vztmpl

pvesh: API por CLI

pvesh expone la API de Proxmox desde la terminal. Útil para scripts o para consultar recursos de forma estructurada.

pvesh get /nodes
pvesh get /nodes/home/qemu
pvesh get /nodes/home/lxc
pvesh get /cluster/resources
pvesh get /nodes/home/storage

# Ejecutar acciones vía API
pvesh create /nodes/home/qemu/101/status/start
pvesh create /nodes/home/qemu/101/status/shutdown
pvesh set /nodes/home/qemu/101/config --memory 1024

# Salida JSON para scripts
pvesh get /cluster/resources --output-format json-pretty

LXC vs Docker vs VM

  • LXC y Docker comparten el kernel del host Linux. Por eso son livianos: no arrancan otro kernel, consumen menos RAM y suelen iniciar más rápido.
  • LXC en Proxmox se usa como contenedor de sistema: se parece a una mini distro Linux (systemd, usuarios, SSH, paquetes). Docker suele usarse más para contenedores de aplicación.
  • VM (QEMU/KVM, lo que maneja qm) emula/virtualiza hardware y ejecuta su propio kernel. Es más pesado, pero necesario para sistemas que no usan el kernel del host.
  • Regla práctica: si podés compartir kernel Linux, LXC/Docker. Si necesitás otro kernel (FreeBSD, OpenBSD, Windows, macOS) o aislamiento más fuerte, VM.

OpenBSD y FreeBSD: VMs, no LXC

FreeBSD y OpenBSD necesitan su propio kernel, así que en Proxmox van como VMs con qm.

VM OpenBSD (creada, lista para instalar)

Se descargó la ISO oficial y se creó la VM 103:

cd /var/lib/vz/template/iso
wget -O openbsd-7.8-amd64-install.iso \
  https://cdn.openbsd.org/pub/OpenBSD/7.8/amd64/install78.iso

qm create 103 --name openbsd \
  --memory 1024 --cores 2 --sockets 1 --cpu host \
  --machine q35 --bios ovmf \
  --efidisk0 local-lvm:0,efitype=4m,pre-enrolled-keys=0 \
  --scsihw virtio-scsi-pci --scsi0 local-lvm:12 \
  --net0 virtio,bridge=vmbr0 \
  --cdrom local:iso/openbsd-7.8-amd64-install.iso \
  --boot 'order=scsi0;ide2' \
  --vga std --ostype other --onboot 0 --serial0 socket

Instalación desde consola:

qm start 103
qm terminal 103          # consola serial; salir con Ctrl+O
# Si usás la UI web, abrir Console. El instalador de OpenBSD es interactivo.

Durante la instalación de OpenBSD, aceptá red por DHCP si está disponible y cuando pregunte:

  • Start sshd(8) by default? [yes] -> yes
  • Crear usuario y permitir login según tu política; para acceso cómodo, agregar tu clave pública luego.

Después de instalar, dentro de OpenBSD:

ifconfig vio0             # ver IP
rcctl enable sshd
rcctl start sshd
# Agregar tu clave pública desde tu Linux:
mkdir -p ~/.ssh && chmod 700 ~/.ssh
# pegar clave en ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

Desde tu Linux:

ssh usuario@IP_OPENBSD
# o con clave explícita
ssh -i ~/.ssh/id_ed25519 usuario@IP_OPENBSD

VM FreeBSD (ya instalada, VM 101)

La VM 101 ya existe. Para darle acceso SSH desde tu Linux:

qm start 101
qm status 101
qm terminal 101           # si tiene consola serial configurada
ip neigh show dev vmbr0   # ver IPs/MACs vistas por el bridge

Dentro de FreeBSD:

ifconfig                  # ver IP, normalmente vtnet0
sysrc sshd_enable=YES
service sshd start

# Crear/usar usuario y agregar tu clave pública
mkdir -p ~/.ssh && chmod 700 ~/.ssh
ee ~/.ssh/authorized_keys   # o vi; pegar tu clave pública
chmod 600 ~/.ssh/authorized_keys

Si querés habilitar login de root por SSH con clave (solo en lab, no recomendable expuesto):

# /etc/ssh/sshd_config
PermitRootLogin prohibit-password
PubkeyAuthentication yes
# luego
service sshd restart

Desde tu Linux:

ssh usuario@IP_FREEBSD
ssh root@IP_FREEBSD       # solo si lo habilitaste con clave

Para encontrar la IP sin consola, una opción es mirar leases/DHCP del router o usar:

ip neigh show dev vmbr0
qm guest cmd 101 network-get-interfaces  # solo si qemu-guest-agent está instalado y activo

¿Cuándo vale Proxmox frente a Arch + libvirt?

Proxmox vale la pena si aprovechás lo que trae integrado:

  • LXC para servicios Linux livianos.
  • Snapshots/backups antes de cambios riesgosos.
  • Plantillas y clones para levantar entornos rápido.
  • Gestión remota por web/API, aunque por SSH también se maneja bien.

Si solo vas a correr una o dos VMs de vez en cuando y ya te sentís cómodo armando todo en Arch con libvirt, virt-manager, scripts o contenedores, Proxmox puede ser una capa extra innecesaria. En hardware justo, la ventaja real no es “más rendimiento”, sino menos fricción para administrar servicios. La regla práctica: usar LXC cuando sea Linux liviano; usar VM cuando el guest necesite su propio kernel.
